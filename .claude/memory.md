- **Date parsing gotcha**: `new Date("YYYY-MM-DD")` parses as UTC midnight, then `.getDay()`/local getters can read back a different calendar day depending on the browser's timezone (classic off-by-one bug). Fixed in day-of-week-calculator and week-number-calculator by splitting the date string into y/m/d integers and using local (`new Date(y, m-1, d)`) or explicit UTC (`Date.UTC(y, m-1, d)`) construction instead of re-parsing the ISO string. Not retroactively fixed in earlier date tools (days-until, age, date-duration, business-days) since their outputs are differences where the error tends to cancel out — worth revisiting if it ever surfaces as a real bug report.

Caught and fixed when first added to bmr/calorie/body-fat calculators (no prior select-field example existed in the codebase to copy from; checkbox-group already used this shape).

  - **Hard lesson on verifying "legible"**: the 6-card version's `elementFromPoint`-at-1-sample-point check reported all badges "visible" but the user still saw unreadable fragments — 1-2 covered pixels passing a boolean check is not the same as a badge being readable. Fixed the verification method itself: sample a 4×3 grid across each badge/title's own bounding box and require the fraction actually topmost, not a single point. Current values hit 100% badge visibility, 67-100% title visibility on all 4 cards, confirmed with this stronger check.
  - **Hard lesson on offset math**: hand-calculated "clearance margins" from card width/rotation were repeatedly wrong in practice (predicted comfortable clearance, actual result was a 1-pixel sliver) — rotation's effect on effective silhouette isn't simple enough to hand-derive reliably. What actually worked: binary-searching each card's offset *live in the browser* (mutating `--tx`/`--ty` via `page.evaluate` and re-measuring visibility immediately) rather than editing source + reloading + rescreenshotting per guess — converged in a handful of steps instead of many. Also found offsetting mostly *vertically* (not horizontally) clears coverage far more efficiently than horizontal offset, because horizontal room is the scarce resource (shared with the text column) while vertical room is nearly free — final values lean heavily on `y` (concrete: `x:-25,y:-220`; bmi: `x:-15,y:-170`; loan: `x:-15,y:-70`) with `rotate` -5°..+4° (moderate, not the wider spread the 6-card version used).

- **Per-calculator "Last updated" dates shipped (082126)** — `build.js`'s `computeCalculatorDates()` runs one scoped `git blame -L <range>` per calculator (NOT a single whole-file blame pass — see code comment) and takes the max commit time across that calculator's own line range as `calc.dateModified`, fed into both the SoftwareApplication schema and a visible `.last-updated` line below the tool intro. **Real bug found and fixed during verification**: a whole-file blame pass silently mis-dates every uncommitted calculator, because all uncommitted working-tree lines share one pseudo-hash (`000...0`) and git's porcelain output only prints full metadata the *first* time a hash appears — later uncommitted hunks elsewhere in the file get collapsed to hash-only lines with no timestamp, so a single pass stamps every one of them with whichever uncommitted edit happens to appear earliest in the file. Fixed by scoping blame per calculator. Also fixed `buildSitemap()`'s static-page dates the same way (`getFileLastModDate()` now checks `git status --porcelain` first — a file with uncommitted changes gets today's date, not its last *committed* date, which was silently stale for every one of this session's edits since almost nothing has been committed). Confirmed real spread across all 77: 41 at 2026-08-17 (untouched since launch), 5 at 08-18, 31 at 08-22 (today's edits) — not everything collapsed to one date.
